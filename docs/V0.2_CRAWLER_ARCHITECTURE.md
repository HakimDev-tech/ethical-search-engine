# V0.2 — Secure Crawler Architecture

- Document ID: ESE-V02-ARCH-001
- Version: 1.0
- Target release: V0.2
- Status: Proposed architecture

## 1. Architectural placement

V0.2 adds one cohesive infrastructure crate, `ese-crawler`, to the existing modular monolith.

It is a library, not a microservice and not a binary application. It does not own search-domain entities, indexing, document policy classification or persistence.

The V0.1 crates remain unchanged unless a concrete integration requirement is discovered and documented. In particular, `ese-domain` stays free of URL, HTTP, DNS and runtime dependencies.

## 2. Proposed crate layout

```text
crates/
├── domain/
├── config/
├── observability/
└── crawler/
    ├── Cargo.toml
    └── src/
        ├── lib.rs
        ├── config.rs
        ├── error.rs
        ├── url_policy.rs
        ├── address_policy.rs
        ├── dns.rs
        ├── transport.rs
        ├── robots/
        │   ├── mod.rs
        │   ├── parser.rs
        │   └── cache.rs
        ├── politeness.rs
        └── engine.rs
```

These are internal modules of one crate, not separate Cargo packages. A module becomes a crate only when independent ownership, reuse or build isolation is demonstrated.

## 3. Responsibility boundaries

### 3.1 url_policy

- Parse untrusted URL input using the URL standard library.
- Enforce scheme, hostname, credentials, port and length policy.
- Produce a canonical request URL and stable origin key.
- Remove fragments.
- Never resolve DNS or perform I/O.

### 3.2 address_policy

- Classify IPv4 and IPv6 addresses against documented special-purpose CIDR ranges.
- Normalize IPv4-mapped IPv6.
- Expose a pure allow/deny decision with a stable reason.
- Keep the address registry policy centralized and testable.

### 3.3 dns

- Define an injectable asynchronous resolver interface.
- Provide a production system-resolver adapter.
- Filter DNS answers through address_policy.
- Return only the approved socket-address set.
- Never allow the HTTP client to independently resolve the same host after validation.

### 3.4 transport

- Build a request-scoped or origin-scoped Reqwest client configured with the validated pinned addresses.
- Enforce GET-only, no redirects, no cookies, no proxy, TLS verification, timeouts and fixed User-Agent.
- Stream response bytes and enforce hard limits.
- Return transport metadata and bounded bytes; do not parse HTML.

### 3.5 robots

- Retrieve robots.txt through the same secure transport path and stricter body limit.
- Parse RFC 9309 semantics using an audited parser.
- Evaluate rules for the ESEBot product token.
- Cache decisions in memory by origin.
- Return explicit allow/deny/unavailable outcomes and reason codes.

### 3.6 politeness

- Enforce a global semaphore.
- Enforce one in-flight request per origin.
- Enforce minimum inter-request spacing and origin cooldown.
- Honor valid Retry-After and supported Crawl-delay values.
- Release permits safely under cancellation.

### 3.7 engine

Orchestrate one explicit seed request:

```text
Input URL
  -> URL policy
  -> DNS resolution
  -> destination filtering and pinning
  -> origin politeness permit
  -> robots cache lookup / secure robots retrieval
  -> robots decision
  -> bounded page GET
  -> typed fetch outcome
```

The engine must not extract links, enqueue URLs, persist state or invoke the ethical policy engine.

## 4. Dependency direction

```text
ese-crawler
  ├── tokio
  ├── reqwest (Rustls, streaming; no compression/cookies)
  ├── url
  ├── ipnet (or approved equivalent)
  └── tracing

ese-domain       (unchanged; no crawler dependency)
ese-config       (unchanged unless future composition requires it)
ese-observability (unchanged)
```

The crawler crate may use the tracing facade but must not require global subscriber initialization to function. Applications own process-level observability setup.

No dependency on Scraper, Tantivy, Axum, PostgreSQL, browser automation or AI runtimes is allowed in V0.2.

## 5. Trust boundaries

Untrusted inputs:
- Seed URL.
- DNS answers.
- HTTP status and headers.
- Redirect Location header.
- robots.txt bytes and directives.
- Response body and content metadata.
- Retry-After and Crawl-delay values.

Trusted only after validation:
- Canonical URL.
- Filtered and pinned socket addresses.
- Parsed robots policy.
- Bounded response bytes.
- Typed fetch outcome.

A redirect Location is always untrusted. V0.2 never follows it.

The response body remains untrusted content. It is not an approved document and must not be sent directly to indexing.

## 6. DNS pinning design

For each request:
1. Parse and validate the URL.
2. If the host is a DNS name, resolve it through the injected resolver.
3. Normalize and classify every returned address.
4. Reject the request if no globally routable address remains.
5. Build the HTTP client with the original hostname mapped only to the approved socket addresses.
6. Preserve the original hostname for TLS SNI and HTTP authority.
7. Disable automatic redirects and ambient proxies.
8. Discard the request-scoped resolution mapping after the fetch.

This design closes the validation-to-connect gap for the HTTP client. It does not eliminate the need for infrastructure-level egress filtering.

## 7. Robots policy flow

The page fetch path must consult the robots cache before requesting page content.

Cache key: normalized origin (scheme, host, effective port).

Cache values:
- Parsed rules with expiry.
- Explicit no-file result (404/410) with expiry.
- Denied/unavailable result with short expiry.

The robots request uses the same destination validation and pinned transport rules. A 3xx response is not followed. The failure matrix in `V0.2_CRAWLER_SPEC.md` is normative.

## 8. Concurrency and state

V0.2 state is process-local and in-memory:
- Global request semaphore.
- Per-origin mutex/semaphore and next-eligible-request timestamp.
- Per-origin robots cache.
- Per-origin Retry-After cooldown.

No state is persisted. Restarting the process clears the cache and politeness history. This limitation is acceptable for a single-process foundation, but a production crawler must later define persistent frontier and politeness semantics before distributed operation.

Origin keys must include scheme and effective port, not merely registrable domain. This avoids accidentally merging distinct services.

## 9. Error and result boundaries

The crate owns its typed errors and stable reason codes. It must not expose raw response bodies or secret-bearing URLs in Display implementations.

Transport errors may retain internal diagnostic sources for debugging, but ordinary tracing fields must be explicitly selected and redacted.

A successful `FetchResult` represents only a bounded HTTP acquisition. It must not be named or documented as an indexed document.

## 10. Test architecture

Production DNS and HTTP adapters are behind injectable interfaces. Unit and integration tests use deterministic fakes to assert:
- Which host and addresses were resolved.
- Which addresses were passed to the connector.
- Whether any second request occurred after a redirect.
- Whether robots was checked before page content.
- Whether body reads stop at the configured limit.
- Whether permits and cooldowns are enforced.
- Whether sensitive fields are redacted.

No CI test may rely on a public DNS server or public website.
