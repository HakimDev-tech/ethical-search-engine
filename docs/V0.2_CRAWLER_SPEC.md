# V0.2 — Secure Crawler Foundation Specification

- Document ID: ESE-V02-SPEC-001
- Version: 1.0
- Target release: V0.2
- Status: Proposed baseline — implementation not authorized by this document alone
- Parent baseline: V0.1 engineering foundation, commit `f33024cdf3e1c65fc26f1093c43bec78563a8dc9`
- Normative terms: MUST, MUST NOT, SHOULD and MAY express requirement strength.

## 1. Objective

V0.2 introduces the first real network-acquisition capability of Ethical Search Engine (ESE): a controlled, security-oriented crawler foundation that can fetch explicitly supplied seed URLs while respecting robots policy and resource limits.

This release is deliberately narrower than a general web crawler. It establishes safe URL intake, destination validation, bounded HTTP retrieval, robots enforcement, host politeness and deterministic tests. It does not discover links or turn fetched HTML into searchable documents.

The crawler is an acquisition component, not a browser, scraper marketplace, proxy, general-purpose HTTP client or search engine.

## 2. Product and security invariants

1. A URL is untrusted input, even when supplied by an operator.
2. A URL must pass syntax, scheme, credential, port and hostname checks before DNS resolution.
3. Every resolved destination must be checked against an explicit public-address policy.
4. The HTTP connection must be pinned to the validated DNS answer for that fetch; a second uncontrolled DNS lookup must not select the destination.
5. Redirects are not followed in V0.2. A redirect is returned as a non-success outcome; it is never permission to contact the Location target.
6. A content request must not be sent until the applicable robots policy has been retrieved and evaluated.
7. A robots retrieval or parsing failure blocks the content request by default, except for the explicit 404/410 absence case.
8. Per-origin politeness and global concurrency limits are enforced by the crawler, not left to callers.
9. Response bodies are streamed and bounded before being retained in memory.
10. Search queries, URL query strings, credentials, cookies and response bodies are not emitted in ordinary logs.
11. A crawler decision must be explainable through a stable outcome/reason code without exposing sensitive request data.
12. Tests must not require public network access.

## 3. V0.2 scope

### 3.1 In scope

- One library crate, `ese-crawler`, with cohesive internal modules.
- HTTP/HTTPS URL parsing and canonicalization.
- Rejection of unsupported schemes, embedded credentials, unsafe ports, malformed hosts and local-only hostnames.
- IPv4/IPv6 destination classification and filtering.
- DNS resolution through an injectable resolver interface.
- DNS answer filtering and connection pinning to the approved addresses.
- HTTP client with certificate validation, no ambient proxy, no automatic redirects and no cookies.
- Bounded, streaming response acquisition.
- Strict content-type allowlist for HTML responses.
- robots.txt retrieval, parsing, matching and in-memory caching.
- ESEBot User-Agent identification.
- Per-origin concurrency and request spacing.
- Global concurrency limit.
- Typed errors and structured, privacy-preserving diagnostics.
- Unit tests, deterministic fake DNS/HTTP integration tests and CI dependency/security checks.
- A small library API that accepts explicit seed URLs and returns a typed fetch outcome.

### 3.2 Explicitly out of scope

- Link extraction, recursive crawling, sitemap discovery or URL frontier persistence.
- HTML DOM extraction, text extraction, metadata extraction or document normalization.
- Canonical-link interpretation and cross-page deduplication.
- Tantivy, BM25, ERE, ranking or indexing.
- Ethical content classification. robots policy is not the ethical policy engine.
- JavaScript execution, headless browsers, rendering or client-side hydration.
- PDFs, images, media, archives, downloads or arbitrary binary content.
- Authentication, cookies, user sessions, form submission or credentialed crawling.
- Proxy support, Tor, rotating IPs, CAPTCHA bypass or anti-bot evasion.
- Distributed crawling, persistent scheduling, PostgreSQL or message queues.
- Automatic retries. A caller may schedule a later attempt after receiving a typed deferred/failure outcome.
- Public API, frontend, production deployment or multi-tenant administration.

## 4. Supported request contract

The public library API should expose an explicit crawl operation over one supplied URL at a time. It must not silently enqueue discovered links.

A successful result contains only acquisition metadata and bounded response bytes, for example:

- Canonical URL after safe normalization.
- Origin identity (scheme, normalized host and effective port).
- HTTP status.
- Validated media type.
- Response byte length.
- Response headers from a strict allowlist or a redacted representation.
- Fetch timestamp.
- Body bytes, only when all checks pass.

The result MUST NOT claim that the body is extracted, normalized, deduplicated, ethically approved or indexed.

The API must distinguish at least:
- URL rejected before network access.
- Destination rejected after DNS resolution.
- robots denied.
- robots unavailable or invalid.
- Host temporarily deferred by politeness or Retry-After.
- HTTP status not accepted.
- Unsupported content type or content encoding.
- Body too large.
- Timeout or transport failure.
- Successful bounded fetch.

Errors must be typed and stable enough for tests and later application orchestration. Raw URLs, query strings and response content must not be embedded in user-facing error strings.

## 5. URL acceptance and canonicalization

### 5.1 Accepted forms

- Schemes: `http` and `https` only.
- Ports: HTTP port 80 and HTTPS port 443 only.
- Host: valid DNS hostname or public IP literal.
- Maximum serialized input length: 8,192 bytes.
- URL userinfo (username/password): rejected.
- Fragment: removed before fetch because it is not sent in HTTP requests.
- Query: preserved exactly as normalized by the URL parser; it is never logged.
- Default ports: omitted in canonical serialization.
- Hostname: IDNA-normalized and lowercased by the URL parser.

### 5.2 Rejected forms

- Any scheme other than HTTP or HTTPS.
- Empty host, malformed host, single-label intranet names, and local-use suffixes such as `.localhost`, `.local`, `.internal`, `.test`, `.invalid` and `.example`.
- Embedded username or password.
- Non-default ports.
- IPv6 zone identifiers.
- URL input longer than 8,192 bytes.
- Control characters or parser-rejected malformed input.

The URL parser is the source of syntax and canonicalization behavior. The crawler must not implement URL parsing through string slicing or ad hoc regular expressions.

## 6. Destination and SSRF policy

### 6.1 Address policy

Only globally routable unicast destinations are eligible. The implementation must deny loopback, private, link-local, unspecified, multicast, broadcast, documentation, benchmarking, shared-address, reserved, transition and other special-purpose ranges.

IPv4-mapped IPv6 addresses must be normalized to their IPv4 address before classification. IPv6 is accepted only from the global-unicast allocation, with explicit exclusions for special-purpose subranges.

The exact IPv4 and IPv6 CIDR policy must be recorded in code and documentation, with provenance to the IANA special-purpose address registries and applicable RFCs. The list must be unit-tested and reviewed when registry data changes. A vague check such as “not RFC1918” is insufficient.

If DNS returns a mixture of allowed and denied addresses, only allowed addresses may be passed to the connector. If no allowed address remains, the request is rejected. The connector must be pinned to the approved set for that fetch.

### 6.2 DNS rebinding and connection pinning

- DNS resolution must be an injectable asynchronous interface.
- The production resolver may use the operating system resolver.
- The resolved addresses must be filtered before the HTTP connection is created.
- The HTTP client must connect only to the filtered address set for the requested hostname.
- The TLS server name and HTTP Host authority must remain the original validated hostname.
- Redirects are disabled, so a remote response cannot cause an unvalidated second request.
- A fresh destination resolution is performed for each new fetch operation; an old address set is not trusted indefinitely.
- Tests must prove that the transport receives only approved addresses and that an unsafe answer never reaches the transport.

### 6.3 Defense in depth

Production deployment SHOULD additionally enforce outbound network egress restrictions at the host/container/network layer. Application-level IP filtering is mandatory but is not a replacement for infrastructure egress controls.

The crawler MUST NOT disable TLS certificate validation. It MUST NOT inherit ambient proxy settings or accept a caller-supplied Host header.

## 7. HTTP transport policy

- HTTPS certificate and hostname validation remain enabled.
- Automatic redirects are disabled.
- Ambient HTTP_PROXY/HTTPS_PROXY configuration is not used.
- Cookies and cookie persistence are disabled.
- No Authorization header is generated.
- No caller-provided Host header is accepted.
- User-Agent is fixed and descriptive: `ESEBot/0.2 (+https://github.com/HakimDev-tech/ethical-search-engine)`.
- HTTP/1.1 is the initial protocol baseline; HTTP/2 is deferred until separately reviewed.
- Request method is GET only.
- Automatic retries are disabled.
- Request timeout: 15 seconds total.
- Connect timeout: 5 seconds.
- Maximum HTML response body: 5 MiB.
- Maximum robots.txt body: 512 KiB.
- Only `text/html` and `application/xhtml+xml` are accepted for page fetches.
- Only identity content encoding is accepted. Compression features must not be enabled in the HTTP client, and a non-identity Content-Encoding is rejected.
- Content-Length is checked before reading when present; streamed byte counting remains authoritative.
- The body is read incrementally and the operation stops immediately when the relevant limit is exceeded.
- A successful page fetch requires HTTP 200. Other statuses are returned as typed non-success outcomes.
- Response headers must be bounded by the HTTP stack and only explicitly selected safe metadata may leave the transport boundary.

The implementation must not buffer an unbounded response and check its size afterward.

## 8. robots.txt policy

### 8.1 Retrieval and matching

Before a page request, the crawler retrieves `/robots.txt` for the exact origin using the same URL, DNS, IP, TLS, timeout, response-size and redirect protections.

The parser must implement the applicable RFC 9309 behavior, including:
- User-agent group selection for the ESEBot product token and wildcard fallback.
- Merging groups with the same most-specific matching user-agent where required by the standard.
- Allow and Disallow rules.
- Longest matching rule precedence.
- Allow winning a same-length tie.
- Correct path matching and percent-encoding behavior.
- Comments, blank lines and UTF-8 handling.

A maintained parser library is preferred over a partial hand-written parser. Its maintenance, license, MSRV, behavior and security posture must be reviewed before the dependency is selected. Unsupported directives must not silently change access decisions.

### 8.2 Failure behavior

| robots response | V0.2 behavior |
|---|---|
| 2xx with valid body | Parse and apply rules |
| 404 or 410 | Treat as no published robots file; proceed subject to all other controls |
| 401 or 403 | Deny crawling for the origin |
| Other 4xx | Deny by conservative product policy |
| 3xx | Do not follow; deny crawling for the origin |
| 5xx | Deny crawling for the origin |
| Timeout, DNS or TLS error | Deny crawling for the origin |
| Oversized or invalid UTF-8 body | Deny crawling for the origin |
| Parser failure | Deny crawling for the origin |

This is intentionally stricter than the minimum behavior some crawlers choose under RFC 9309. ESE will not interpret an inability to read the policy as permission to fetch.

### 8.3 Cache and extensions

- Robots decisions are cached in memory by exact origin.
- Successful policy and 404/410 absence results may be cached for up to 24 hours.
- Failure/denial outcomes may be cached for up to 5 minutes to prevent request storms.
- The robots cache is capped at 10,000 origins; expired entries are evicted first, then least-recently-used entries. It must never grow without bound.
- Per-origin politeness/cooldown state is also bounded to 10,000 origins. An active origin entry is never evicted; when capacity is exhausted, new origins are deferred until capacity is available.
- Cache entries expire and are revalidated; no persistent robots cache is introduced in V0.2.
- A valid `Crawl-delay` extension, if present, is treated as a conservative additional delay. It is not assumed to be part of RFC 9309. Invalid values or values above 24 hours cause the origin to be deferred rather than ignored.
- Sitemap directives are not followed in V0.2 because link discovery is out of scope.

## 9. Politeness and resource budgets

Default limits:

| Limit | V0.2 default | Hard rule |
|---|---:|---|
| Global in-flight requests | 8 | Config may lower, never raise |
| In-flight requests per origin | 1 | Fixed |
| Minimum spacing between requests to an origin | 1 second | Config may increase, never lower |
| Page response body | 5 MiB | Fixed maximum |
| robots.txt body | 512 KiB | Fixed maximum |
| URL input | 8,192 bytes | Fixed maximum |
| Connect timeout | 5 seconds | Fixed maximum |
| Total request timeout | 15 seconds | Fixed maximum |
| Redirects | 0 | Fixed |
| Automatic retries | 0 | Fixed |

Origin identity includes scheme, normalized host and effective port. Host-level controls must not be bypassed by changing URL paths or query strings.

HTTP 429 and 503 responses must not trigger an automatic retry. A valid Retry-After value must create an origin cooldown; malformed values fall back to a conservative local cooldown. The crawler returns a deferred outcome so a future scheduler can decide when to retry.

All concurrency permits must be released on success, error, timeout and cancellation.

## 10. Privacy and observability

Ordinary logs may include:
- A request correlation identifier.
- A stable, non-reversible origin fingerprint or normalized hostname only where operationally necessary.
- Request duration, response status, byte count and stable outcome code.
- Policy/parser version and cache hit/miss state.

Ordinary logs MUST NOT include:
- Raw URL query strings or fragments.
- URL userinfo.
- Cookies, Authorization headers or credentials.
- Full response bodies.
- Arbitrary response headers.
- User search queries.
- Personal data extracted from pages.

Debug logging must obey the same privacy boundary. Redaction must occur before fields are passed to tracing, not only in a log formatter.

## 11. Dependency and crate policy

Create exactly one new crate: `ese-crawler` at `crates/crawler`.

Initial direct runtime dependencies are expected to be:
- Tokio for asynchronous runtime, networking, synchronization and time.
- Reqwest with Rustls and streaming support, with compression and cookie features disabled.
- `url` for standards-based URL parsing and canonicalization.
- `ipnet` (or an equally auditable alternative) for explicit CIDR classification.
- `tracing` for structured diagnostics.

A robots parser dependency is not selected until a focused maintenance, license, MSRV and RFC-conformance review is recorded. Exact versions and enabled features are selected during implementation and audited by the existing cargo-deny policy.

The crawler crate must not depend on `ese-domain` merely to reuse generic types. It must not introduce Scraper, Tantivy, database, AI or browser dependencies. No new crate is justified for a module that can remain cohesive inside `ese-crawler`.

## 12. Testing strategy

Tests must use injected DNS and HTTP boundaries. The default test suite must be deterministic and offline.

Required test families:
- URL parsing, canonicalization and rejection.
- IPv4 and IPv6 address classification, including boundary cases and IPv4-mapped IPv6.
- Mixed DNS answer filtering and empty-safe-set rejection.
- Proof that only pinned safe addresses reach the transport.
- Redirect response does not cause a second request.
- TLS/transport failure handling.
- robots group selection, wildcard fallback, longest-match precedence and allow tie.
- robots failure matrix and cache expiry.
- Per-origin serialization, request spacing and global concurrency.
- Retry-After cooldown behavior.
- Content-Length and streamed body-size enforcement.
- Unsupported content types and content encodings.
- Cancellation releases permits.
- Redaction of URL queries, credentials and response content.
- No public network calls in CI.

Property-based testing MAY be added if it materially improves URL/IP/robots boundary coverage and the dependency cost is justified.

## 13. Completion and release gate

V0.2 is accepted only when:
1. All mandatory criteria in `V0.2_CRAWLER_ACCEPTANCE.md` pass.
2. CI passes on the final implementation commit.
3. The declared MSRV is checked against all new direct and transitive dependencies.
4. No unresolved critical or high-severity advisory remains.
5. SSRF, DNS pinning, redirect, robots and response-limit tests pass.
6. The crawler does not perform link discovery or any out-of-scope behavior.
7. Documentation matches actual code and dependency features.
8. A validation report records commit, toolchain, test evidence, security findings and limitations.

A crawler that merely fetches a URL is not accepted if its destination, robots, privacy or resource controls are incomplete.
