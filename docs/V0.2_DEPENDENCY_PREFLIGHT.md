# V0.2 — Dependency and API Preflight

- Document ID: ESE-V02-PREFLIGHT-001
- Version: 1.0
- Review date: 2026-11-14
- Target: V0.2 Secure Crawler Foundation
- Status: API review complete; parser compatibility gate must pass in the Phase 1 integration spike
- Scope: dependency and API research only; no runtime dependency or crawler code is added by this document

## 1. Executive result

The selected transport architecture is feasible with the existing Rust 1.85.0 MSRV:

- Reqwest 0.13.5 exposes request-level DNS overrides through `resolve_to_addrs`.
- The original URL hostname remains the request authority; the override changes the socket addresses used for connection establishment.
- A fresh client per fetch isolates the DNS pin from Reqwest's connection pool.
- Reqwest supports explicit proxy disabling, redirect disabling and retry disabling.
- Response bodies can be consumed incrementally with `Response::chunk()`; the separate `stream` feature is not required for this bounded loop.
- Tokio, URL, IP network and HTTP-date parsing crates have compatible declared MSRVs.
- `robotxt` 0.7.0 is not compatible with the current MSRV because it declares Rust 1.90. The older `robotxt` 0.6.1 is the preferred parser candidate, but it must pass the Rust 1.85 build and our RFC 9309 conformance fixtures before it is accepted as a runtime dependency.

No dependency is approved merely because it is listed below. Cargo resolution, cargo-deny and the MSRV job remain mandatory before implementation proceeds beyond the integration spike.

### 2.1 Tokio feature set

Use `default-features = false` and enable only the features required by the implementation:

- `net`: system DNS lookup through Tokio's networking API.
- `time`: request deadlines, origin spacing and cooldowns.
- `sync`: semaphores and per-origin synchronization.
- `rt`: runtime-dependent async primitives and test runtime.
- `macros`: deterministic async tests.

Do not enable `full` or introduce Tokio into the domain, config or observability crates.

### 2.2 Reqwest feature set

Use:

```toml
reqwest = {
    version = "=0.13.5",
    default-features = false,
    features = ["rustls"]
}
```

Do not enable `default-tls`, `native-tls`, `http2`, `system-proxy`, `cookies`, `gzip`, `brotli`, `zstd`, `deflate`, `charset`, `json`, `multipart` or `blocking`.

The implementation should use `Response::chunk()` in a bounded loop. Reqwest exposes this method without the optional `stream` feature; `bytes_stream()` is the API that requires that feature. Omitting `stream` avoids enabling additional stream dependencies without reducing the required functionality.

The `rustls` feature is explicit and the default feature set is disabled. TLS certificate and hostname verification must remain enabled. Never call the dangerous certificate or hostname verification bypass methods.

### 2.3 URL and IP policy

Use `url` for parsing and normalization. Do not hand-parse URL authorities, IDNA hostnames or percent-encoding.

Use `ipnet` only as a CIDR utility. It does not provide the crawler's security policy. The project owns a reviewed, static IPv4/IPv6 range table with provenance and boundary tests.

The source of truth for special-purpose ranges is the IANA IPv4 and IPv6 Special-Purpose Address Registries. The registries were last updated on 2025-10-09 at review time. The implementation must record the snapshot date and must not fetch registry data at runtime.

Relevant registries:
- https://www.iana.org/assignments/iana-ipv4-special-registry
- https://www.iana.org/assignments/iana-ipv6-special-registry
- https://www.rfc-editor.org/rfc/rfc6890

The security policy must explicitly cover private, loopback, link-local, shared, documentation, benchmarking, multicast, unspecified, reserved, unique-local, IPv4-mapped IPv6, transition and translation ranges. Conservative blocking of a larger aggregate is acceptable where a more-specific global exception would create ambiguity. Any exception must be justified and tested; do not infer global reachability from the fact that an address is absent from a short hand-maintained list.

### 2.4 Robots parser selection

Preferred candidate: `robotxt = "=0.6.1"`, with default features disabled and only `parser` enabled.

Reasons:
- The crate documents RFC 9309 robots matching and the `crawl-delay` extension.
- It separates parsing/matching from HTTP retrieval, which preserves our secure transport boundary.
- It has a small, focused API and MIT licensing.
- Version 0.7.0 is actively maintained but declares Rust 1.90, so it cannot be adopted without a separate MSRV decision.

Caveats:
- Version 0.6.1 has no declared MSRV in the metadata reviewed. It is not yet proven against Rust 1.85.
- The current 0.7.0 documentation is not proof that every behavior is identical in 0.6.1.
- Parser matching must be tested against our own RFC 9309 fixtures before approval.
- Required cases include user-agent selection, merging multiple matching groups, wildcard fallback, longest-match precedence, Allow on equal-length ties, terminal `$`, wildcard `*`, percent-encoding, UTF-8 handling and empty rules.
- `Crawl-delay` is an extension, not part of RFC 9309. The adapter must validate its numeric representation and enforce the product's 24-hour maximum. Invalid or excessive values must defer the origin; they must never silently become zero.
- If 0.6.1 fails the MSRV or conformance gate, stop and reassess. Do not silently raise the workspace MSRV or replace the parser with an unreviewed implementation.

The parser is not responsible for fetching robots.txt, interpreting HTTP status codes, caching, politeness or DNS policy.

## 3. Reqwest API verification and required configuration

Reqwest 0.13.5 provides the required APIs:

| Requirement | API / configuration | Required use |
|---|---|---|
| Pin DNS to validated addresses | `ClientBuilder::resolve_to_addrs` | Pass only filtered socket addresses for the exact hostname |
| Preserve scheme port | SocketAddr port `0` | Reqwest uses the conventional scheme port; the URL's explicit port takes precedence |
| Disable ambient proxies | `ClientBuilder::no_proxy()` | Call explicitly even with default features disabled |
| Disable redirects | `redirect(reqwest::redirect::Policy::none())` | All 3xx responses remain visible to policy code |
| Disable protocol retries | `retry(reqwest::retry::never())` | Reqwest's default may retry protocol NACKs |
| Restrict protocol | `http1_only()` | Keep HTTP/1.1 as the V0.2 baseline |
| Bound connection phase | `connect_timeout(...)` | Use the specified five-second limit |
| Bound total operation | `timeout(...)` | Use the specified fifteen-second limit |
| Bound stalled reads | `read_timeout(...)` | Apply an explicit read timeout consistent with the total deadline |
| Incremental body read | `Response::chunk()` | Count actual bytes before appending each chunk |
| Avoid Referer leakage | `referer(false)` | Do not generate a Referer header |
| Avoid automatic decompression | Minimal features; no compression features | Send `Accept-Encoding: identity` and reject non-identity Content-Encoding |

### 3.1 DNS pinning and client lifetime

For each HTTP fetch:

1. Parse and validate the URL.
2. Resolve the hostname using the injectable resolver.
3. Normalize and filter every returned IP address.
4. Reject the operation if no permitted address remains.
5. Build a new Reqwest client with `resolve_to_addrs(host, approved_addrs)`.
6. Send the original hostname URL through that client.
7. Drop the client after the fetch completes.

Do not replace the URL hostname with a literal IP. The hostname is needed for the HTTP authority and TLS SNI/certificate verification. Do not share a client or connection pool across separate DNS validation operations.

This is an application-level control. Production must additionally enforce outbound network restrictions at the container, host or infrastructure boundary.

### 3.2 Retry and redirect semantics

Reqwest 0.13.5 retries some low-level protocol failures by default. The explicit `retry(reqwest::retry::never())` call is mandatory; merely omitting a retry wrapper does not disable the default behavior.

Automatic redirects are disabled. The application must inspect status codes and must not follow a Location header in V0.2.

### 3.3 Streaming and hard limits

Use `Response::chunk()` and enforce the byte ceiling against the actual accumulated bytes. A declared Content-Length is an early rejection hint, not the authoritative limit. The stream loop must reject before appending a chunk that would exceed the configured maximum.

No call to `bytes()`, `text()` or any API that buffers the entire response before applying the limit is allowed.

## 4. HTTP-date and Retry-After

Use `httpdate 1.0.3` for HTTP-date parsing. It declares Rust 1.56 and MIT OR Apache-2.0 licensing.

The application owns the policy:
- Parse delta-seconds without integer overflow.
- Parse HTTP-date and compare it with the current system time.
- Clamp or reject values according to the documented maximum cooldown policy.
- On missing or malformed values, use the specified 60-second fallback for 429/503.
- Never retry the request automatically.

## 5. Deliberate protocol-policy deviations

The current V0.2 design is deliberately more conservative than the behavior permitted or recommended by RFC 9309 in some retrieval cases.

### 5.1 robots.txt redirects

RFC 9309 recommends following at least five consecutive redirects when retrieving robots.txt, including redirects across authorities; a successfully reached file applies to the initial authority.

V0.2 follows no redirects. A robots 3xx therefore blocks the page fetch. This is a deliberate security-first deviation, not full RFC 9309 retrieval conformance. The parser can still implement RFC 9309 matching semantics. Any later redirect support must be manual, bounded and revalidate every destination through URL, DNS and IP policy while applying the resulting rules to the initial authority.

### 5.2 robots.txt error statuses

RFC 9309 treats 4xx responses as an unavailable robots file, while 5xx/network failures are unreachable. ESE intentionally denies on 401, 403 and other non-404/410 4xx outcomes rather than treating them as permission. 404/410 remain the only statuses treated as an absent policy file in V0.2. This is a stricter product policy and must remain explicit in documentation and tests.

These deviations must not be described as complete RFC 9309 retrieval compliance.

## 6. Dependency and feature exclusions

Do not add these dependencies unless implementation evidence requires them:
- `futures-util`: not needed for `Response::chunk()`.
- `bytes`: chunks can be handled through the returned value's byte slice.
- `async-trait`: native async functions in traits are available within the selected MSRV; use generic injection unless dynamic dispatch is proven necessary.
- `mime`: validate the bounded Content-Type value with a small, tested parser unless a real need for the MIME crate appears.
- `thiserror`: use crate-owned typed errors; add a derive dependency only if it materially improves maintainability.
- Hickory DNS: the system resolver is sufficient for the first implementation; a custom resolver is not justified yet.
- Any browser, HTML extraction, persistence, index or search dependency.

## 7. Mandatory integration gates

Before the crawler implementation is considered ready to proceed:

1. Add the candidate dependencies only to `ese-crawler`, not to the existing domain/config/observability crates.
2. Generate and commit Cargo.lock through Cargo; never hand-edit lock entries.
3. Run `cargo +1.85.0 check --workspace --all-targets --locked`.
4. Run `cargo deny check`; do not widen the license allowlist without an explicit review.
5. Verify the resolved Reqwest feature tree contains no HTTP/2, proxy, cookie or compression features.
6. Verify the resolved robots parser version is exactly 0.6.1 and is not yanked.
7. Run the RFC 9309 matching fixture suite and the explicit product-policy deviation tests.
8. If any gate fails, stop and document the blocker before continuing.
