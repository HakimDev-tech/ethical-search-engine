# V0.2 — Secure Crawler Implementation Plan

- Document ID: ESE-V02-PLAN-001
- Version: 1.0
- Target: V0.2
- Status: Proposed plan; no implementation performed
- Depends on: accepted V0.1 engineering foundation

## 1. Goal

Implement the smallest real crawler capability that satisfies the security and politeness contract in `V0.2_CRAWLER_SPEC.md`.

The release accepts explicit seed URLs and returns bounded HTML response bytes only after URL validation, safe destination resolution, robots approval and politeness checks.

No recursive crawling, HTML extraction, persistence, index or search capability is part of this plan.

## 2. Locked decisions before coding

- One library crate: `ese-crawler`.
- Tokio for asynchronous I/O, introduced only in the crawler crate.
- Reqwest with Rustls and streaming; no automatic redirects, cookies, compression or ambient proxy.
- `url` for URL parsing and canonicalization.
- `ipnet` or approved equivalent for CIDR policy.
- Injectable DNS resolver and HTTP transport boundaries.
- Explicit IANA-derived public-address policy with DNS pinning.
- RFC 9309 robots matching; parser dependency selection requires a separate audit.
- In-memory robots cache and per-origin politeness state only.
- No automatic retries or link discovery.
- Existing cargo-deny and MSRV gates remain mandatory.

Exact crate versions and the robots parser are not frozen in this plan. They must be selected with evidence during dependency preflight, not guessed.

## 3. Implementation sequence

### Phase 0 — Dependency and API preflight

- Review current compatible Tokio, Reqwest, URL, IP-network, robots parser and HTTP-date crates.
- Record the API and dependency review in `V0.2_DEPENDENCY_PREFLIGHT.md`.
- Select minimal feature sets.
- Evaluate robots parser candidates for RFC 9309 behavior, maintenance, security history, license and MSRV.
- Verify Reqwest can pin a hostname to validated socket addresses while preserving TLS SNI and HTTP authority.
- Verify explicit disabling of Reqwest's default protocol retries, system proxy and redirects; use `Response::chunk()` for bounded streaming without enabling the optional `stream` feature.
- Verify no ambient proxy, redirect, cookie or compression feature is active.
- Record exact versions and decisions in the V0.2 ADR document.
- Run cargo-deny and MSRV checks before implementation.

**Exit gate:** no unresolved dependency or API blocker; direct dependencies and features approved.

### Phase 1 — Crate and pure URL policy

- Add `crates/crawler` to the workspace.
- Create crate root, local config and typed errors.
- Implement URL parse/canonicalize/reject behavior.
- Add stable origin key.
- Add exhaustive URL unit tests.

**Exit gate:** invalid URLs fail before any resolver or transport call.

### Phase 2 — Address policy and DNS pinning

- Implement IPv4/IPv6 special-purpose range policy with documented provenance.
- Normalize IPv4-mapped IPv6.
- Define async resolver trait and production adapter.
- Filter mixed DNS responses.
- Implement request-scoped pinned Reqwest client/connector.
- Preserve hostname for TLS and HTTP authority.
- Add tests proving unsafe addresses never reach transport.

**Exit gate:** SSRF and DNS-rebinding acceptance tests pass.

### Phase 3 — Bounded HTTP transport

- Configure TLS, no proxy, no cookies, no redirects and fixed User-Agent.
- Enforce GET-only behavior and request timeouts.
- Stream body bytes and enforce Content-Length plus actual byte limits.
- Reject unsupported media and content encoding.
- Return typed outcomes and safe metadata only.

**Exit gate:** response-size, redirect, timeout and content-type tests pass without public network access.

### Phase 4 — robots policy

- Integrate the audited parser.
- Retrieve robots.txt through the secure transport path.
- Implement failure matrix and conservative deny behavior.
- Implement user-agent selection and matching semantics.
- Add bounded in-memory cache with expiry, a 10,000-origin capacity and eviction.
- Bound per-origin politeness state to 10,000 origins; evict idle entries only and defer new origins when all entries are active.
- Enforce the same URL/DNS/transport constraints for robots requests.

**Exit gate:** RFC matching tests and all failure-matrix tests pass; no page request bypasses robots.

### Phase 5 — Politeness and engine orchestration

- Add global semaphore (default 8, hard maximum 8).
- Add per-origin serialization (exactly one in-flight request).
- Enforce minimum one-second spacing.
- Parse and enforce valid Crawl-delay extension values; defer invalid or greater-than-24-hour values.
- Implement Retry-After cooldown for 429/503.
- Ensure cancellation releases all permits.
- Compose URL, DNS, robots, politeness and page fetch in one explicit seed operation.

**Exit gate:** concurrency, spacing, cooldown and cancellation tests pass.

### Phase 6 — Privacy, observability and CI

- Audit every tracing event and error Display implementation.
- Ensure URL query strings, credentials, response bodies and arbitrary headers are redacted before event creation.
- Add architecture checks and dependency feature review.
- Update cargo-deny policy only when a dependency license requires an explicit owner decision; do not silently widen the allowlist.
- Run formatting, metadata, check, build, Clippy, tests, docs, cargo-deny and MSRV checks.

**Exit gate:** full CI passes with locked dependencies and no public-network test.

### Phase 7 — Final review

- Review every V2-AC criterion against code and test evidence.
- Review the exact dependency tree and enabled features.
- Review SSRF/IP policy provenance and boundary tests.
- Review robots behavior and its documented conservative deviations.
- Review privacy logs and failure messages.
- Confirm no V0.3+ feature entered the crate.
- Produce a final validation report.
- Keep the PR draft until explicit acceptance.

**Exit gate:** all mandatory V0.2 criteria pass; no unresolved critical/high advisory; PR not merged automatically.

## 4. CI command baseline

The V0.2 pipeline must preserve all V0.1 gates and add crawler-specific tests:

```bash
cargo fmt --all -- --check
cargo metadata --no-deps --format-version 1
cargo check --workspace --all-targets --locked
cargo build --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo doc --workspace --no-deps --locked
cargo deny check
cargo +1.85.0 check --workspace --all-targets --locked
```

Tests must be offline and deterministic. The crawler's production networking adapter must be tested through fakes and controlled local fixtures, not public endpoints.

## 5. Principal risks

| Risk | Mitigation |
|---|---|
| SSRF through URL or DNS | URL allow policy, special-range filtering, pinned IPs, no redirects, egress firewall |
| DNS rebinding | Resolve and pin per fetch; test that transport uses only approved addresses |
| Incomplete robots parser | Audited RFC 9309 parser and conformance fixtures |
| robots failure interpreted as permission | Explicit conservative failure matrix |
| Decompression bomb | Compression disabled; identity encoding only |
| Unbounded response | Streaming byte counter and hard limits |
| Crawl overload | Global/per-origin gates and request spacing |
| Sensitive URL leakage | Redaction before tracing |
| Dependency/MSRV drift | Locked versions, cargo-deny and MSRV CI |
| Scope creep | No links, extraction, index, persistence or browser in V0.2 |

## 6. Definition of complete

V0.2 is complete only when all criteria in `V0.2_CRAWLER_ACCEPTANCE.md` are demonstrated by code and automated tests, the final CI is green, documentation matches implementation and the review report records residual risks.

A successful request to one public URL is not, by itself, evidence that the crawler is secure or complete.
